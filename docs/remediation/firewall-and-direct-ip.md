# پیکربندی فایروال و ارتباط مستقیم بین‌سروری (Firewall & Direct-IP Debug Mode)

این مستند تشریح می‌کند که چگونه فایروال سرورها (UFW و زیرلایه iptables) پیکربندی شده است تا در حالت Direct-IP، ترافیک میان‌سروری بین VPS1 (`81.12.50.30`) و VPS2 (`31.56.89.69`) به شکل دوطرفه و کاملاً امن برقرار شود، بدون آنکه پورت‌های داخلی به روی عموم اینترنت باز شوند یا زنجیره‌های امنیتی دچار Flush و اختلال گردند.

---

## ۱. اصول ایمنی و معماری فایروال

1. **عدم اختلال در نشست‌های فعال SSH:** تمام رول‌های پیش‌فرض و رول‌های ویژه SSH با پورت ۲۲ در ابتدای زنجیره قرار دارند تا خطر قطعی دسترسی ادمین (Lockout) به صفر برسد.
2. **عدم بازگشایی پورت‌های داخلی به اینترنت عمومی:** پورت‌های حیاتی زیرسیستم‌ها مانند دیتابیس‌ها، NFS، K3s API، لاگ‌استش و مانیتورینگ تحت هیچ شرایطی به روی کل اینترنت (`0.0.0.0/0`) باز نمی‌شوند.
3. **اعمال محدودیت بر مبنای IP همتا (Peer IP Whitelisting):** دسترسی تنها برای آدرس IP معتبر سرور دیگر صادر می‌شود.
4. **حفظ استانداردهای UFW و iptables بدون فلاش کردن (No Flush):** تمامی قوانین از طریق ساختارهای رسمی UFW در `/etc/ufw/before.rules` و `/etc/ufw/after.rules` و دستورات `ufw allow` استاندارد تزریق می‌شوند.

## ۲. مقابله با دور زدن فایروال توسط کوبرنتیز و داکر

### ۲.۱. محدوده NodePort در کوبرنتیز (۳۰۰۰۰ تا ۳۲۷۶۷)
کوبرنتیز ترافیک پورت‌های NodePort را در لایه NAT و FORWARD هدایت می‌کند که به طور پیش‌فرض قوانین لایه INPUT در UFW را دور می‌زنند. برای جلوگیری از این رخداد، در جدول RAW بسته قبل از رسیدن به جدول روتینگ پردازش می‌شود:

**در `/etc/ufw/before.rules` (جدول RAW):**
```text
*raw
:PREROUTING ACCEPT [0:0]
# در حالت اشکال‌زدایی مستقیم، فقط IP سرور همتا مجاز است:
-A PREROUTING -i eth0 -s 31.56.89.69 -p tcp --dport 30000:32767 -j ACCEPT
-A PREROUTING -i eth0 -s 31.56.89.69 -p udp --dport 30000:32767 -j ACCEPT
# برای تمامی سایر آدرس‌های اینترنت عمومی، ترافیک بلافاصله Drop می‌شود:
-A PREROUTING -i eth0 -p tcp --dport 30000:32767 -j DROP
-A PREROUTING -i eth0 -p udp --dport 30000:32767 -j DROP
COMMIT
```

### ۲.۲. پورت‌های پابلیش‌شده داکر (زنجیره DOCKER-USER)
سرویس Docker به طور پیش‌فرض با دستکاری مستقیم iptables و جدول FORWARD قوانین UFW را دور می‌زند. مطابق مستندات رسمی داکر، کنترل این ترافیک باید در زنجیره `DOCKER-USER` انجام شود:

**در `/etc/ufw/after.rules` (زنجیره DOCKER-USER):**
```text
*filter
:DOCKER-USER - [0:0]
# پذیرش ترافیک فقط از سرور همتا:
-A DOCKER-USER -i eth0 -s 31.56.89.69 -j ACCEPT
# مسدودسازی هرگونه اتصال جدید ورودی از اینترنت عمومی به کانتینرها:
-A DOCKER-USER -i eth0 -m conntrack --ctstate NEW -j DROP
-A DOCKER-USER -j RETURN
COMMIT
```

## ۴. دستورالعمل ارزیابی و راستی‌آزمایی رول‌های فایروال

### ۴.۱. بررسی وضعیت رول‌ها روی VPS1 و VPS2
```bash
# بررسی وضعیت رول‌های سطح بالای UFW همراه با شماره ردیف:
ufw status numbered

# بررسی رول‌های تزریق شده در زنجیره DOCKER-USER:
iptables -L DOCKER-USER -n -v --line-numbers

# بررسی رول‌های محافظت از NodePort در جدول RAW:
iptables -t raw -L PREROUTING -n -v --line-numbers
```

### ۴.۲. آزمون برقراری ارتباط از نود مقابل (Connectivity Test)
از سرور **VPS2** (`31.56.89.69`) به سمت **VPS1** (`81.12.50.30`):
```bash
# بررسی دسترسی به پورت K3s API:
nc -zvw3 81.12.50.30 6443

# بررسی دسترسی به پورت NFS:
nc -zvw3 81.12.50.30 2049

# بررسی دسترسی به رجیستری داکر:
nc -zvw3 81.12.50.30 5000
```

از سرور **VPS1** (`81.12.50.30`) به سمت **VPS2** (`31.56.89.69`):
```bash
# بررسی دسترسی به پورت پرومتئوس:
nc -zvw3 31.56.89.69 9090

# بررسی دسترسی به پورت لاگ‌استش:
nc -zvw3 31.56.89.69 5044

# بررسی دسترسی به نود اکسپورتر ورکر:
nc -zvw3 31.56.89.69 9100
```

### ۴.۳. آزمون عدم نفوذ از اینترنت عمومی (Negative Test)
از یک سرور یا سیستم شخص ثالث (خارج از رنج این دو سرور):
```bash
# پورت‌های داخلی باید مسدود یا فیلتر باشند:
nc -zvw2 81.12.50.30 6443    # باید Connection timed out دهد
nc -zvw2 81.12.50.30 2049    # باید Connection timed out دهد
nc -zvw2 31.56.89.69 9090    # باید Connection timed out دهد
```
